# P4-02.0 — Frame 几何字段消费者审计

- **日期**：2026-07-29
- **测量 HEAD**：`a39e8cfc`
- **性质**：只做审计，未改代码
- **结论**：**P4-01b 高估了可回收量**。四个切片长度不是纯几何，
  它们同时编码「窗口是否已安装」，并有三条构造后改动路径。
  干净可回收约 **20–36 B**，不是 68 B —— **P4-02.1 单独跨不过 192 B 边界**

---

## 0. 阻塞点不存在（P4-01b 的误报）

P4-01b 把 `core/object.zig:1071-1077` 标为「整片交换 `frame.locals` / `frame.args`」
的阻塞点。**该处不是 `exec.frame.Frame`。**

```zig
pub const SuspendedFrameStorage = struct {   // core/object.zig:998
    storage: []JSValue = &.{},
    locals: []JSValue = &.{},
    args: []JSValue = &.{},
    var_refs: []*VarRef = &.{},
    open_var_refs: []?*VarRef = &.{},
};
```

这是 generator/async 挂起期间**停放缓冲区所有权**的独立记录，
`swapOwned` 交换的是它自己的字段。它不在 `Entry` 里，
**与 Entry 的 256 字节完全无关**。当时的 grep 命中的是 `self.frame.locals`，
而那个 `self.frame` 是一个 `SuspendedFrameStorage`。

阻塞点解除。但审计随即发现了一个**更实质**的问题。

## 1. 四个切片长度不是纯几何

### 证据一：长度为 0 是一种载荷状态

```zig
// vm_gen_async.zig:318-320，为 resident generator 建立新帧时
std.debug.assert(frame.storage_values.len == 0);
std.debug.assert(frame.locals.len == 0 and frame.args.len == 0);
std.debug.assert(frame.var_refs.len == 0 and frame.open_var_refs.len == 0);
```

resident generator 帧在窗口安装前 `locals.len == 0`，
而同一个 `function.var_count` 可以非零。
`vm_gen_async.zig:72` 明确写 `frame.locals = &.{};`。

**所以 `locals.len` 同时回答两个问题：「这个函数有几个局部」与
「这一帧的窗口现在装上了没有」。** 从 `function.var_count` 推导只能回答第一个。

`Frame.deinit` 与 `isEmpty` 也依赖 `len == 0` 跳过工作
（`frame.zig:374-377`、`:606`）。

### 证据二：构造后确实会改动

| 路径 | 改动 | 命中（fib/identity/empty/countdown） |
|---|---|---|
| `frame.zig:834` `ensureVarRefsCapacity` | **增长** `var_refs` | **0 / 0 / 0 / 0** |
| `frame.zig:863` | 替换 `locals` 存储 | 未计数 |
| `vm_gen_async.zig:72` | 置 `locals = &.{}` | generator 专有 |
| `inline_calls.zig:2526` | `var_refs = target.captureSlice()`（借用别名） | 每次普通调用 |

`ensureVarRefsCapacity` 的注释自陈是给畸形/合成 bytecode 兜底
（"Normal compiled bytecode is sized exactly, so reject this malformed/synthetic
growth case"），四个普通 workload 命中皆为 **0** —— 但它存在，
因此 `var_refs.len` 在类型层面是可变量。

### 证据三：现有代码把存储长度当作待校验量

```zig
// frame.zig:704-707
const count = self.function.openVarRefCount();
if (self.open_var_refs.len != 0) {
    if (self.open_var_refs.len != count) return error.InvalidBytecode;
```

派生值 `count` 已经存在，存储长度是被它**校验**的对象 ——
这条最接近「冗余」，但它同样用 `len != 0` 区分已安装/未安装。

## 2. 消费者规模

| 字段 | 读取点（排除 tests） | 主要形态 |
|---|---:|---|
| `frame.var_refs.len` | **43** | `idx >= len` 边界检查、`len != 0` 安装判定、容量增长 |
| `frame.locals.len` | **36** | `idx >= len` 边界检查（`InvalidBytecode`）、`len == 0` 判定 |
| `frame.args.len` | 19 | 同上 |
| `frame.open_var_refs.len` | 9 | `len != 0` 判定、与派生 count 校验 |
| `frame.storage_values.len` | 4 | 仅所有权/释放 |
| `stack.capacity` | 11 | backing 视图、`setLen`/`setTopPtr` 断言、grow |

边界检查改用 `function.var_count` 等派生值在**正确性上等价**，
但它们从「一次字段加载」变成「经 `frame.function` 的二次加载」——
是搬移而非消除。

## 3. 修正后的可回收量

| 项 | P4-01b 估计 | **本轮修正** | 理由 |
|---|---:|---:|---|
| 四个切片长度 | 32 | **0（纯推导不可行）** | 兼编码「已安装」状态，且有三条构造后改动路径 |
| `stack.capacity` | 8 | **8（有条件）** | arena 窗口帧成立；grow 路径需另行处理 |
| `stack.values` | 8 | **8（有条件）** | `= locals.ptr + locals.len`，断言已存在，但依赖可变的 `locals.len` |
| `planned_stack_bytes` | 4 | **4** | 代码自陈重算是 Debug lockstep guard |
| `stack.memory` | 8 | **8（安全）** | `&rt.memory`，运行时全局，无第二重语义 |
| `stack.policy` | 8 | **8（安全）** | `rt.vm_stack_arena_policy`，运行时全局 |
| **合计** | **68** | **16 安全 + 20 有条件 = 36** | |

**`256 − 36 = 220`，仍是四条 cache line。P4-02.1 单独跨不过 192 B。**

## 4. 保留大部分收益的替代设计

长度不能纯派生，但可以**用一个共享标志承载「已安装」语义**，
把长度本身交给 FrameLayout：

```text
现在：五个 []T          = 80 B   （ptr + len，len 兼作安装标志）
改为：五个 [*]T + 1 位  ≈ 41 B   （长度来自 FrameLayout，安装状态来自该位）
回收 ≈ 39 B
```

配合 §3 的 36 B：`256 − 75 ≈ 181` → **三条 cache line**。

⚠️ 但这需要改动 **107 个读取点**（43+36+19+9），
且每个 `idx >= len` 检查都要换成经 `frame.function` 的派生值 ——
**这不再是「零消费者改动」的低风险刀**，与 P4-01b 的推荐前提相反。

## 5. 对路线的影响

P4-01b 的推荐建立在「68 B 不需要改任何消费者语义」之上，该前提**不成立**：

```text
P4-01b 推荐：
    P4-02.1 先做 FrameLayout，风险低于 PlainEntry     <- 前提被证伪
```

修正后的现实是：

| 方案 | 回收 | Entry | 消费者改动 |
|---|---:|---:|---|
| 只做安全项（Stack 两个全局字段） | 16 | 240 | 极少 |
| 加上有条件项 | 36 | 220 | 中等（grow 路径） |
| 加上「长度入 FrameLayout + 安装位」 | 75 | 181（**3 线**） | **107 个读取点** |
| 再加 PlainEntry 的 Extended 与打包 | 128 | 128（**2 线**） | 全部消费者 |

**跨过 192 B 边界必须做到第三档，而第三档的改动面已经与 PlainEntry 同量级。**
因此 P4-01b 里「先 FrameLayout 后 PlainEntry，两者可分别归因」的拆分
在工程上不成立 —— 它们共享同一批消费者。

## 6. 建议

```text
不建议：按 P4-01b 的拆分推进 P4-02.1
        （其「零消费者改动」前提已被证伪）

建议在两条中选一：

A. 只落地 16 B 的安全项（Stack 的 memory/policy 移到 Machine/runtime 查取）
   Entry 256 -> 240，不跨线，预期时间收益接近零。
   价值是表示清理，不是性能刀 —— 应按 refactor 而非 perf 提交。

B. 承认 Frame/Stack 表示改造是一件事，一次性设计
   （长度入 FrameLayout + 安装位 + Extended + 打包，目标 128 B），
   接受 107+ 消费者改动与一次大范围语义门禁，不再拆成两笔。
```

⚠️ 无论哪条，P4-00 的告诫仍然成立：**空间存在不等于时间存在**。
普通返回触达全部四条线且热字段分散其上；`256 → 181` 或 `→ 128`
是否兑现为 `fib_rec` 的时间收益，没有任何现有证据支持。

在投入 B 之前，值得先用一次**廉价的时间证伪实验**回答
「cache line 数是不是瓶颈」—— 例如用 `-Dzjs_dossier_layout_pad` 之类的现成手段
制造已知的行数差异并观察 `fib_rec`，而不是先花大量改动再发现瓶颈在别处。

## 7. 限制

- `frame.zig:863` 的 `locals` 替换路径未做动态计数；
- 边界检查改用派生值的**指令成本**未量化（多一次 `frame.function` 间接）；
- 未评估把「已安装」语义改由 `teardown` 现有位承载的可行性；
- 全部为静态审计，无任何时间证据。
