# 决策简报：是否让 opcode 分派 ABI 用寄存器承载栈顶值

日期 2026-08-13　zjs `53734c2a`　对照 QuickJS `04be2460`
本文自足，不需要读其它报告。**需要外部判断的是最后一节的三个问题。**

---

## 0. 一句话

zjs 的浮点/数值运算**吞吐比 QuickJS 快 22%，但在依赖链上只快 0%**（实际慢 4%），
因为每条 opcode 的结果都要经解释器栈往返一次，两个引擎都付这笔约 7–8 cyc 的钱。
**zjs 的 tail-call threaded 分派理论上可以把栈顶值留在寄存器里绕开它，QuickJS 的
computed goto 做不到。** 问题是：这值得改吗，以及它算不算越过了「忠实重实现」的边界。

---

## 1. 背景：这个项目的约束

zjs 是 QuickJS 的**忠实 Zig 重实现**。已生效的硬约束：

- 唯一的性能标尺是 QuickJS；不拿 zjs 旧版本当尺。
- **不得引入 QuickJS 没有的 fast path / bypass / 特化**（有 lint 强制）。
  已有先例：`constructSimpleFieldConstructor` 这条 zjs-only 构造快路径被裁定必须删除，
  即使删了会让分数变差。
- 忠实性优先于数字：若对齐 QuickJS 让某个数字变差，如实报告并保留对齐。
- 最终裁决指标是 **zoo（Octane）分数**，不是 cycles。

当前状态：zoo throughput geomean **0.9137**（15 基准），距追平 9.4%。

---

## 2. 触发问题的基准

`navier-stokes` 分数 **0.971**，是所有落后基准里最接近 1.0 的一个。
它是流体模拟，热循环（`navier-stokes.js:576`）：

```js
lastX = x[currentRow] = (x0[currentRow] + a*(lastX + x[++currentRow] + x[++lastRow] + x[++nextRow])) * invC;
```

`lastX` **跨迭代自依赖**，所以整条循环跑在关键路径上。数组是 plain `new Array(size)`，
不是 Float64Array。

### 定工作量 PMU（8 samples ABBA，绑 CPU 19，`--iteration-divisor 16`）

| 计数器 | z/q | 说明 |
|---|---:|---|
| instructions | **0.9645** | zjs 少执行 3.6% 的指令 |
| cycles | **1.0562** | 却多花 5.6% 的周期 |
| IPC | 0.9229 | |
| stall_backend | 1.5566 | +205.8M |
| **stall_backend_mem** | 1.1191 | **+0.43M，占超出的 0.5%** |
| stall_frontend | 1.0114 | +0.69M，0.7% |
| br_mis_pred_retired | 1.0044 | +704，0.0% |

**超出 +92.3M cycles 的 100% 是非访存后端停顿。** 不是缓存、不是分支、不是前端、
也不是「干的活更多」——zjs 干的活反而更少。

---

## 3. 受控实验：吞吐 vs 延迟

三个微基准，8 samples ABBA，绑 CPU 19，减去同形状空循环。
每条算术运算的成本（`s = s*a + b` 含 2 条算术）：

| | zjs | qjs | z/q |
|---|---:|---:|---:|
| **串行**（单链自依赖，延迟受限） | **10.53** | **10.14** | **1.038** |
| **独立**（四条并行链，吞吐受限） | **6.74** | **8.61** | **0.783** |

纯整数对照（`s = (s+a) & b`，全程 int32）：

| | zjs | qjs | z/q |
|---|---:|---:|---:|
| 串行 | 13.71 | 14.47 | **0.948** |
| 独立 | 13.98 | 16.32 | **0.857** |

**读法**：
- zjs 的数值**吞吐**明显更好（浮点 0.783、整数 0.857）。
- 一旦串行化，浮点上 zjs 的优势完全消失（1.038）；整数上仍保持（0.948）。
- **两个引擎的串行绝对成本都是约 10 cyc/运算**，而 `fadd` 本身只要 2–3 cyc。
  ⇒ **约 7–8 cyc 是解释器往返本身**，两边都付。

### 边际斜率（固定循环次数，只改每次 loc 往返里的算术条数：2 / 4 / 8）

| | 每条算术的边际 cyc |
|---|---|
| 浮点 | zjs **11.33** vs qjs **10.66** |
| 整数 | zjs **6.50** vs qjs **5.88** |

每条算术 zjs 只慢 **0.6 cyc**，浮点整数一致。**不是浮点特有的缺陷，是一个均匀的小常数。**
（截距为负，说明线性模型不干净，截距不可解释，只用斜率。）

## 4. 反汇编：两个引擎的浮点臂形状几乎相同

**zjs**（`opBinary__struct_116935.hnd`）：
```
ldur x11, [x1,#-32]     ; 用通用寄存器加载 payload
fmov d0, x11            ; GP → FP 跨域
ldr  x10, [x8]          ; 第二个操作数，同样 GP
fmov d1, x10            ; 又一次跨域
fadd d0, d0, d1
stur d0, [x1,#-32]      ; 用 FP 寄存器存回 payload
stur x9, [x1,#-24]      ; 存 tag
ldrb w9, [x0,#1]!       ; 取下一条 opcode
br   x4                 ; 尾调用
```

**qjs**（`JS_CallInternal` 内 `CASE(OP_add)` 的浮点臂，`quickjs.c:19710-19722`）：
```
fmov d1, x2             ; GP → FP 跨域
fmov d0, x0             ; 同样跨域
fadd d0, d0, d1
stur x0, [x19,#-24]     ; 存 tag
stur d0, [x19,#-16]     ; FP 存回 payload
ldrb w1, [x8],#1
br   x0
```

**结论：qjs 做的是一模一样的事**——同样 GP 载 payload、同样两次 `fmov` 跨域、同样 FP 存回。
两边都是 16 字节 JSValue（payload + tag），都经栈往返。

## 5. 今天在这条线上被证伪的假设（用于评估本简报的可信度）

同一天，在「找到了机制」这件事上翻车四次，每次都是「指令序列看着对得上、数字也吻合」：

| 假设 | 证伪方式 | 结果 |
|---|---|---|
| 调用边界的成本可以靠删指令拿回 | 逐项分解定价 | 上限 geomean **+0.234%** |
| RayTrace 的 cache-miss 2.89x 值 25% 的差距 | 核实 PMU 事件语义 | 那是 **L1 refill，99.8% 是 L2 命中**，真 LL miss 仅 15.2K，值 0.047% |
| `Vm.pc` 重发布形成 3–5 级关键路径链 | 双探针 + 阳性控制（强塞一条链能稳定检出 +2.32 cyc） | 生产代码**没有那条链**，上限 **0.000%** |
| 帧复用子系统的记账是每次调用的税 | 出线口计数器 | 普通 `op_call2` 对复用状态的读写**全为 0**；删掉它 zoo 三 pad 全败 |
| （本文）跨域 `fmov` 是 zjs 特有的额外成本 | 反汇编 qjs | **qjs 做同样的事**，假设作废 |
| （本文）zjs 的链比 qjs 长 4.5 cyc | 拆出绝对值 | 实际只长 **4%**；4.5 是「串行化惩罚之差」，被我误读 |

**所以本简报刻意区分「已测事实」与「未验证推断」**，见下节。

## 6. 已确立 vs 未确立

**已确立（有对照、有重复、可复算）**
1. navier-stokes 少 3.6% 指令、多 5.6% 周期，超出 100% 是非访存后端停顿。
2. 数值运算：zjs 吞吐快 22%（浮点）/ 14%（整数）；串行时浮点优势归零、整数仍保持。
3. 串行绝对成本两边都约 10 cyc/运算，而 FP 加法本身 2–3 cyc。
4. 两个引擎的浮点臂指令序列形状相同。
5. 每条算术的边际差只有 0.6 cyc，浮点整数一致。

**未确立（本决策的关键缺口）**
- ❌ **那约 7–8 cyc 的「往返」里，具体有多少是 store→load 的转发延迟、
  多少是 tag 处理/分派/其它？没有测过。**
- ❌ 把栈顶值放进寄存器能省掉其中多少？**没有原型，没有定价。**
- ❌ 收益是否只集中在链式算术负载（navier-stokes、box2d 部分循环），
  还是能惠及全部 15 个基准？**未普查。**

---

## 7. 提案

**把 opcode 分派 ABI 从 `(pc, sp, var_buf, vm)` 扩展为携带栈顶 1（或 2）个 JSValue。**

链式算术时，`fadd` 的结果直接留在寄存器里交给下一个 handler，
不再「存回栈 → 下一个 handler 载回 → `fmov` → 用」。

**为什么只有 zjs 能做**：zjs 的 handler 之间用 `musttail` 互跳、参数走寄存器；
qjs 是一个大 C 函数内的 computed goto，`sp[-1]` 对通用情况必须落内存，
它的 C 局部集合是固定的。这条正好是 zjs 已测出的架构优势的延伸——
**zjs 每条 opcode 比 qjs 便宜 15%（2.218 vs 2.611 cyc），空循环 0.781。**

### 已知成本与风险

1. **ABI 变更波及全部约 200 个 handler**，每个都要维护不变式。
2. ⚠️ **GC rooting 是正确性地雷**：只存在于寄存器里的 JSValue 对 GC 的栈扫描不可见，
   任何可能分配的路径之前必须先落栈。漏一处就是难复现的内存错误。
   本项目有先例：构造帧的 `teardown.simple` 只在 ReleaseSafe 才 abort，
   test262 全量和所有语义测试都没抓到。
3. **寄存器压力**：JSValue 是 16 字节 = 2 个寄存器；`callconv(.c)` 现用 4 个参数寄存器，
   再加 2 个可行但会挤压 handler 内部。
4. ⚠️ **有负面先例**：2026-07-14 的「精益全单体 dispatch」91 个臂全绿但 PMU **4/4 回退**，
   被判为 LLVM 生态局部最优并冻结。**大型分派 ABI 改动在本仓库有过败绩。**
5. **收益未定价**（见 §6）。

### 收益的诚实边界

- navier-stokes 现在 0.971，超出 +92.3M cycles。若往返部分能砍掉一半，
  它有机会反超；但**这是外推，不是测量**。
- 只有**关键路径上的链式运算**受益。吞吐受限的循环本来就是 zjs 赢。
- 全 zoo 的覆盖面未知。

## 8. 需要外部判断的三个问题

**Q1（边界问题，最重要）**
把栈顶值放进分派 ABI，**算不算越过「忠实重实现」的边界**？
- 支持「不算」：它不改任何可观察语义，也不是针对某个形状的特化；
  它是**分派约定**，和「用 musttail 而不是 switch」同一类选择，而 zjs 早已如此。
- 支持「算」：QuickJS 没有这个东西，而项目的 anti-goal 规则是
  「不得引入 QuickJS 没有的机制」，且已经据此裁定删除过一条 zjs-only 快路径。
  另有登记：「IC / fusion = 换赛道作弊」「op 空间是战略储备，不动」。
  这条介于两者之间。

**Q2（投入产出）**
在收益完全未定价、且同类大型 ABI 改动有过 4/4 回退先例的情况下，
是否值得先做一个**只覆盖 2–3 条 opcode（add / mul / get_loc）的原型**来定价？
（原型本身也要改 ABI，只是不铺开；成本估计是数天。）

**Q3（优先级）**
即使 Q1 判定可做、Q2 定价为正，它是否应该排在其它未解问题之前？当前并列的还有：
- **PdfJS 约 137M cycles（其赤字的 60%）是尚未命名的宏观机制**——
  两侧执行的 opcode 数几乎相同（z/q 0.9973），现有的调用/属性/opcode 模型全部解释不了。
  PdfJS 是当前最大缺口（0.778）。
- 每次 JS→JS 调用有 **12.46 cyc/call 的无主后端停顿**，已被六条独立诊断证明
  「弥散、无单点、不属于任何可命名子系统」。
