## 0. 两处必须收紧的表述

先前的汇报把两个具体实验的结论推得过宽，已更正：

**NaN boxing 的实验**证明的是：
> 当前这套 NaN-boxed 表示**及其生成代码**，在串行浮点链上严重回退。
> （nanbox/tagged，layout=plain：`dep.js` insn 1.3252 / cyc 1.5026 / stall_backend 2.2511）

它否掉了「把 JSValue 从 16 字节压成 8 字节就能解决问题」这个**朴素宽度假设**，
但它**不是纯宽度实验**——同时改变了 tag 判定、浮点装箱/解箱和依赖链。
因此它**没有否掉**：
> 保持 16 字节表示，仅通过跨 handler forwarding 打断 store→load 依赖。

**cand1 的实验**证明的是：
> **cand1 这一个具体变换**拿延迟换吞吐。

它**不能**推出「任何 stack-cache 或 forwarding 都必然拿延迟换吞吐」。
若 cand1 本身就是跨 handler 值承载，它会直接否掉该类具体 ABI 形态；
若不是，两者关联更弱。**因此核实 cand1 的代码形态是必要的。**

## 1. d12-fpchain：**REJECTED**，仅保留为诊断证据

cand1 **不需要**等 pad7 重测即可裁决。已满足三个独立否决条件：

- D10 判据的最坏 pad 为 **0.9992**，门禁失败；
- 目标基准 navier-stokes **五个 pad 全部回退**（0.9945–0.9990，零翻转）；
- 稳定伤害 earley-boyer(0.9962)、raytrace(0.9975)、mandreel(0.9973) 等当前重要缺口。

状态：**Rejected optimization, retained as diagnostic evidence.**
允许收尾的唯一理由是「受益/受害分组」可能揭示一个**可迁移的性能分类轴**，
而不是 cand1 还有落地可能。

### 允许的收尾范围（仅此四项）

1. **重测受污染的 pad7**（该窗口内曾有另一任务误占同核）。
   不重跑其余 pad，也不得因 pad7 结果变化而开始调 cand2/cand3。
2. **确认 cand1 的精确代码形态**，报告必须明确：
   改了哪些数据依赖 / 是否跨 handler 承载值 / 是否减少 store-load /
   是否增加 GP↔FP transfer / 是否改变 handler ABI /
   是否造成 spill、live range 延长或寄存器压力变化。
3. **解释分组，但只能给出证据支持到的层级**。至少比较：
   dependent microbench 的 cycles/op；independent microbench 的 throughput；
   各 zoo benchmark 的 cycles / instructions / backend stalls；
   benchmark 响应是否与 dependent/independent 特征稳定相关。
4. **给出绝对 PMU 数值**。⚠️ `indep stall_backend = 5.1798x` 出现在 cycles 反而下降的情况下，
   很可能受较小基数、事件重叠或事件语义影响。
   **不得用该比率单独解释机制，必须同时给出 raw delta 与 stall/cycle。**

### 不允许

- 不再尝试修改 cand1 以挽救 navier；
- 不做新的 pad 扫描；
- 不因 geomean 中位 +0.41% 讨论落地；
- **不把「串行受害、吞吐受益」上升为所有 forwarding 机制的普遍定律。**

⇒ d12 只剩一份**机制尸检报告**，不再是一条优化线。

## 2. stack-cache-sim：**继续完成模拟**，但结果只测机会、不证可落地性

不因 d12 的两个结果提前终止。理由不是沉没成本，而是它回答的问题**尚未被回答**：

> 真实 zoo workload 中，跨 opcode 的值存活形态到底有没有足够广的 forwarding 机会？

NaN boxing 回答的是**表示**问题；cand1 回答的是**某个实现变换**的 latency/throughput 取舍；
动态模拟回答的是 **workload opportunity**。三者不是同一个实验。
且它不触碰 handler，风险很低。

### 结果必须拆成两档

**A. Read-forwarding opportunity**（内存中的 stack slot 仍然 authoritative）
- producer 仍然写回 stack；handler ABI 同时携带一个值副本；
- 紧邻 consumer 直接使用副本，从而消除 **load**；
- ownership / teardown / cold publication 基本保持原状。
- 它测试能否打断 `store result → next handler → load same result`。
- ⭐ **这是当前最值得保留的最小机制**：不需要延迟 materialization，也不需要重定义 live stack。

**B. Write-back cache opportunity**（值只在寄存器里，晚些再写入 stack）
- 可同时消除 store 与 load；
- 但改变 canonical stack publication，触及 RC ownership、exception、stack grow、
  frame switch 与 teardown；正确性成本远高于 A。

> **若模拟只有 B 显著而 A 几乎没有机会 → 直接停止，不进入 ABI harness。**
> 当前证据不足以支持为了额外消除 store 而重写整个 live-stack 不变量。

### 报告必须增加的三个维度

不能只统计「可消除多少次 load/store」，还要：

1. **producer-consumer 距离与 cache depth**：距离 1 的机会 / 需要 depth 2 的机会 /
   需要任意深度 slot 的机会 / **`get_loc b` 之类的 push 导致的驱逐比例**。
2. **连续存活长度**：一个 cached value 能跨几个 handler / 平均多少 edge 后 flush /
   **是否大部分机会只存活一个 edge**。
3. **flush 原因**（分类计数）：control-flow join / call·native·helper / possible allocation /
   stack grow / exception seam / unknown stack effect / generator·async suspension /
   unsupported opcode。

⇒ 用来区分「表面上 traffic 很多」与「值一进缓存就被 flush」。

### 原门槛降级 + 新增第二阶段硬门槛

原门槛「至少两个非 navier benchmark 有显著可消除的 stack traffic」**保留**，
但只作**必要条件**，**不再是**进入生产 ABI 改造的充分条件。

即使模拟通过，最多批准一个**独立 codegen harness**，并新增硬门槛：

> **dependent chain 不得回退。**

第二阶段必须同时满足：dependent microbench 至少不回退（最好改善）；
independent throughput 改善；empty dispatch 不回退；无新增 spill；handler frame 不增长；
**不出现 cand1 那种「instructions 下降但 dependent cycles 上升」的形态**。
出现即停止，不进入 zoo 集成。

## 3. pdfjs-diagnosis：**PRIMARY**，P2 优先拆 string/regexp，转主线待 P2 后定

主线名称仍是 **PdfJS mechanism diagnosis**，不是 string/regexp optimization。

P1 已证明三件事：宏观赤字可稳定归属（覆盖 **97.6–97.9%**）；
`dispatch / hot handlers` 最大但机制密度可能低、较弥散；
**`string / regexp +70M` 是稳定正赤字且此前从未触碰，机制密度可能更高**。

### P2 调查优先级（立即调整）

```
1. string / regexp
2. call entry / return
3. dispatch / hot handlers
4. property / array
```
排序依据不是绝对赤字，而是 **可命名性 × 可干预性 × 未探索程度**。

### RegExp 基准领先不构成反证

`regexp` benchmark 为 1.114 只说明 zjs 在该 workload 上整体领先，
**不能**证明 PdfJS 的 string/regexp 区域没问题。可能原因：
PdfJS 主要花在字符串拼接/切片/flatten 而非 regexp matching；
pattern·flag·capture·lastIndex·compile/match 比例不同；
regexp helper 周围的字符串转换或结果 materialization 更贵；
benchmark 测稳态而 PdfJS 偏 compile-heavy；
**区域分桶把字符串与 regexp 放在一起，+70M 可能几乎全是字符串。**

### P2 第一件事：继续拆开该区域，至少分为

```
regexp compile ; regexp execute ; match/capture result construction
string concat / rope ; string flatten ; substring / slice
string compare / hash / atomization ; encoding or representation conversion
other string helpers
```
同时必须区分：**调用次数更多** vs **调用次数相同、单次成本更高**——
两类机制的解决方向完全不同。

### 正式转主线的门槛

- 找到一个稳定子区域，至少解释约 **25–30M cycles**；**或**解释 string/regexp 赤字的 **≥40%**；
- **8/8 样本方向稳定**；
- 能明确归因到 call count / bytes processed / flatten count / allocation count / cycles-per-call 之一；
- 有可执行的**阳性控制**与**消融实验**。

满足后正式升级为第一优化主线。
**若 +70M 被十几个小项均匀分散、没有单项超过约 10–15M，则不值得开优化线**，
下一优先级转向 `call entry / return +62M`。
