## 1. 机制

```zig
fn normalizedReciprocalInit(divisor: Limb) Limb            // qjs udiv1norm_init, quickjs.c:11433
inline fn divTwoByOneReciprocal(high, low, divisor, recip) // qjs udiv1norm,      quickjs.c:11444
const reciprocal_threshold: usize = 3;                     // qjs UDIV1NORM_THRESHOLD
```

`m = na − nb >= 3` 时预计算一次 reciprocal，之后每个商位用乘法型估算；
低于阈值仍走 `u128 / u64`。**其余一切未动** ——
scratch 分配、归一化、第二 limb 修正、multiply-subtract、add-back、符号、结果构造，
单 limb 路径也未改。

`top == v1` 的 clamp 分支在 reciprocal 之前，所以 helper 的前置条件 `high < divisor` 恒成立。

## 2. 正确性最强门禁：helper 与宽除法**逐次相同**

`divTwoByOneReciprocal` **不是近似**。测试
`reciprocal two-by-one division is exactly the wide division`：

- 8 个边界除数（`2^63`、`2^63+1`、`maxInt`、`maxInt−1`、`0xC000…`、`0x8000…0001` 等）
  × 6 个 `high`（`0`、`1`、`divisor−1`、`divisor−2`、`divisor/2`、`divisor/2+1`）
  × 8 个 `low`（`0`、`1`、`maxInt`、`2^63`、`2^63−1`、交替位…）；
- **1 000 000 组随机** normalized divisor；
- 额外 **200 000 组**偏置到 `2^63` 与 `maxInt` 两个极端（reciprocal 最大与最小处）。

每一组都要求商与余数与 `(high:low) / divisor`、`% divisor` **完全相等**。

## 6. 为什么只有 10%：**已实测，不是 codegen 问题**

按 PRD 要求，宽除法次数已达 `D → 1` 而改善仍在 10% 附近，先查 codegen：

| 检查 | 结果 |
|---|---|
| helper 是否真正内联 | **是**（0 符号） |
| 是否被编译成意外 helper | **否**（helper 内无任何 `bl`） |
| 是否产生额外 spill | **否** —— IPC **4.65 → 4.65 完全不变** |
| code size 是否让 subMul 退化 | **否** —— multiply-subtract 的 limb 迭代数逐项相同（§2） |

指令与周期**同步下降**：

| case | insn/op P0 → P1 | Δ | cyc/op P0 → P1 | Δ | IPC |
|---|---:|---:|---:|---:|---|
| `8x4` | 2720.1 → 2460.2 | **0.9045** | 585.0 → 529.5 | **0.9051** | 4.65 → 4.65 |
| `16x8` | 4426.5 → 3887.0 | 0.8781 | 1083.7 → 937.5 | 0.8651 | 4.08 → 4.15 |
| `16x4` | 4450.0 → 3643.0 | 0.8186 | 1153.5 → 899.5 | 0.7798 | 3.86 → 4.05 |
| `2x2` | 1799.7 → 1797.5 | 0.9988 | 293.7 → 292.7 | 0.9968 | 6.13 → 6.14 |

由 `8x4`（5 商位）与 `16x4`（13 商位）两点解出：

```text
__udivti3            ≈ 82 条指令
reciprocal estimate  ≈ 13.5 条指令      —— 6 倍差距，helper 编译得很紧
```

于是 `8x4` 的天花板是可算的：

```text
删除   5 × 82 = 410 条
新增   1 × 82（init）+ 5 × 13.5 = 149 条
净省   261 条 / 2720 条 = 9.6%      实测 9.55%（0.9045）
```

### ⚠️ 更正我在 P6-04d0 里的收益预估

P6-04d0 预测 `8×4` 146 → 112–118 ns，依据是 `udivmod` 的
**perf cycle 占比 34.78%**。实测是 146 → 131 ns。

原因：**cycle 占比高估了可兑现的收益。**
`__udivti3` 是一个低 IPC 的软件循环，它的延迟本来就被乱序引擎部分掩盖了；
删掉它，剩余工作把腾出的周期吸收掉。
本轮 `8x4` 的 insn 比与 cyc 比是 0.9045 / 0.9051 —— **几乎完全一致**，
说明真正兑现的是**指令占比（约 15%）**，不是周期占比（34.78%）。

**方法学结论**：预估这类「删除一个高延迟 helper」的收益时，
应当用**指令占比**而不是 cycle 占比作上界；cycle 占比只有在该 helper 真正造成前端/后端 stall
时才可兑现，而本例 IPC 不变已经排除了这一点。

## 7. 需要裁决的两处

### 7.1 `8×4` / `16×8` 的 15% 门槛与 JS 5% 门槛

机制完全正确、方向全部一致、没有任何 eligible 形态变慢，
但**这个机制在 `8×4` 上的数学上界就是 9.6%**（§6），15% 无法由 d1 单独达到。
`16×8`（9 商位）拿到 13.9%，`16×4`（13 商位）拿到 22.7%、`24×8` 19.7% ——
**商位越多越接近门槛**，因为 init 的一次性成本被摊薄。

建议按 P6-04c 的先例作**显式 waiver**（而不是写成通过），
理由是机制门槛全达、无回退、且 d2a/d2b 针对的是另一块成本（`8×4` 的 JS 分配器占 26.3%）。

### 7.2 `6×4` +1.04%

`m = 2`，低于阈值，**算法路径完全没变**，纯粹是代码增长/布局。
16/16 组合同向，geomean 1.0104，绝对量 **1.3 ns**。
`5×4`（m=1）与 `9×8`（m=1）都跨 1.0，只有紧贴阈值下方的这一个形态受影响。

⚠️ **不建议现在调阈值去掩盖它**（PRD 明确禁止）。
建议同样记为哨兵，与 `mod-size-2x1` 一起在 d2a/d2b/d2c 每一刀复测。

## 9. 限制

- 两项性能门槛未达（§7.1），按 waiver 提请裁决，未粉饰为通过；
- `6×4` 的 +1.04% 未追（§7.2）；
- reciprocal 只用于**多 limb** 路径；单 limb 路径（P6-04b）的逐 limb 循环
  **也可以用同一个 helper**，本刀按 PRD 边界未动，未测其潜在收益；
- 阈值固定为 3（与 qjs 一致），**未做动态阈值搜索**；
  `6×4`（m=2）的 3 次宽除法是否值得启用，需要单独比较阈值 2 与 3；
- 指令数拆解（82 / 13.5 条）由两个形态两点解出，**未在第三个形态上交叉验证**；
- JS 层只有三个除法 case，等宽形态在 JS 层仍未覆盖。
