## 1. 为什么必须重拆

P6-04d0 的模型建立在 `6 allocations`、无 reciprocal、有 abs clone 的形态上：

```text
d0：  固定 57–68 ns   +   商位 × (12.43 + 1.372·nb)
```

此后三刀（d1 reciprocal、d2a 删 clone、d2b 按需物化）**同时削了固定成本与估算成本**，
d0 的系数已经全部失效。**不能用旧模型判断 d2c。**

⚠️ 另有一个新的非线性：`reciprocal_threshold = 3` 使 `m < 3` 与 `m >= 3` 成为**两段不同斜率**，
d0 时不存在。因此本轮**分段拟合**，不再用两端点求斜率。

### 2.5 与 d0 的对照

| | d0 | **d2.5** |
|---|---|---|
| 固定成本 | 57–68 ns | **46.9–49.5 ns** |
| 每商位常数项（估算） | 12.43 ns | **5.81 ns** |
| 每商位 nb 项（multiply-subtract） | 1.372 · nb | **1.460 · nb** |
| `8×4` | 146.3 ns | **109.24 ns** |
| `16×8` | 272.7 ns | **209.08 ns** |

估算常数项 12.43 → 5.81 是 d1 的 reciprocal；固定 57–68 → 47–49 是 d2a+d2b。
**`nb` 项基本不变** —— multiply-subtract 从未被碰过，符合预期。

⚠️ 三条轴的截距在 46.9–49.5 之间一致（±3 ns），但**不能靠相减把 reciprocal init 从截距里分离出来**：
轴一（无 init）46.93 与轴二 eligible（有 init）49.48 只差 2.6 ns，
而 perf 给 `udivmod` 在 `8×4` 上是 8.52% × 109.24 = **9.3 ns**。
这两个数不自洽，说明 eligible 段的外推截距吸收了一部分非线性。
**可靠的是「固定 ≈ 47±3 ns」这个量级本身，不是它的内部拆分。**

## 4. 符号级归因

### 4.1 direct-core（`init.gpa` = libc malloc，分配器占比被高估）

| shape | 商位 | long division | **分配器合计** | `udivmod` | `divRemAllocOutput` |
|---|---:|---:|---:|---:|---:|
| `2×2` | 1 | 23.99% | **42.9%** | 11.96% | 15.57% |
| `8×4` | 5 | 57.64% | **22.0%** | 8.52% | 6.52% |
| `16×8` | 9 | **77.80%** | 8.6% | 5.15% | 2.50% |
| `24×8` | 17 | **87.89%** | 3.8% | 1.98% | 1.53% |

`8×4` 的分配器绝对值 = 22.0% × 109.24 = **24.0 ns**，摊在 3 次分配 + 3 次释放上。

**`16×8` 77.8% / `24×8` 87.9% 已经几乎纯内核** —— 这正是 d2a/d2b 对它们收益递减的原因。

### 4.2 JS 层（真实路径，slab 分配器）

| 符号 | `div_8x4`（2.68x qjs） | `div_16x8`（1.33x） | `mod_8x4`（1.53x） |
|---|---:|---:|---:|
| `divRemAbsNormalizedLong` | 33.60% | **64.87%** | 38.44% |
| `MemoryAccount.allocAlignedBytesNoTrigger` | 9.87% | 4.29% | 7.27% |
| **`SmallObjectSlab.addArena`** | **6.77%** | — | **6.13%** |
| **`_int_malloc`（arena refill）** | **4.91%** | — | **5.41%** |
| `MemoryAccount.freeAlignedBytes` | 3.55% | — | 2.26% |
| **`unlink_chunk`** | **1.85%** | — | **2.30%** |
| **分配器合计** | **≈27.0%** | ≈4.3% | **≈23.4%** |
| `udivmod` | 3.22% | 3.67% | 3.04% |
| `exec.value_ops.binary` | 9.49% | 6.99% | 10.92% |
| `core.bigint.BigInt.createFromOwned` | 2.30% | 2.20% | — |

### ⚠️ 一个必须记录的发现：**分配次数减半，JS 层分配器占比没变**

P6-04d0 测到 `div_8x4` 的 JS 层分配器占比是 **26.3%**（当时 6 次分配）。
现在是 **27.0%**（3 次分配）。**次数砍半，占比不动。**

原因在细分里：`addArena` 6.77% + `_int_malloc` 4.91% + `unlink_chunk` 1.85% = **13.5%
是 arena 的创建与销毁**，而不是每次分配的簿记。slab 一旦某个 size class 的最后一个块被释放
就把 arena 还给 backing allocator（见 `core/memory.zig` 与 P6-03e 的记录），
而这个 workload 每次操作都把它分配的块全部释放 ——
**所以每次操作都在新建又销毁 arena，代价与分配次数无关，只与被触及的 size class 数量有关。**

这对 d2c 有直接含义（§5）。

## 5. 裁决：情况 B，d2c 有价值

按 PRD 的判据：

| 判据 | 阈值 | 实测 | |
|---|---|---|---|
| 情况 A（不做 d2c） | digit ≥60 ns **且** fixed ≤35–40 ns | digit **58.3**，fixed **49.5** | 不成立 |
| **情况 B（做 d2c）** | **fixed ≥45 ns** | **fixed 49.5 ns** | **成立** |

### 收益预估（两条独立口径）

**direct-core**：分配器 24.0 ns 摊在 3 次分配上，合并 `u`+`v` 去掉 1 次分配 + 1 次释放
→ 约 **8 ns** → `109.2 → ≈101 ns`，**约 −7.3%**。
与 PRD 情况 B 里的算术（`108 → 100，约 7%`）一致。

**JS 层**：更有希望也更不确定。合并去掉的不只是一次分配，
还可能**去掉一个被触及的 size class**，从而减少 arena churn（§4.2 的 13.5%）。
- 若 `u`+`v` 的合并块落进一个**已被其他分配占用**的 class → churn 不减，收益仅≈分配次数那部分；
- 若它让触及的 class 数从 3 降到 2 → 收益可能**大于** 7%。

⚠️ **这是基于 §4.2 机制的推理，不是测量。** d2c 必须实测，不得引用本节数字作为结论。

## 6. 对 d3 的输入（若 d2c 之后仍需继续）

`16×8`（77.8% 内核）与 `24×8`（87.9% 内核）已经**没有固定成本可削**。
它们的 1.33x 也已经很接近。真正仍在 2x 之外的只有 `div_8x4`（2.68x），
而它是 **45% 固定 / 53% 逐商位** 的混合形态。

若 d2c 后 `div_8x4` 仍在 2x 之外，逐商位内核的可查项按本轮数据排序：

```text
每商位 = 5.81 + 1.460·nb
         ^^^^   ^^^^^^^^^^
         估算    multiply-subtract（nb 次 limb 迭代，从未被优化过）

nb=4 时：估算 5.81 (50%)  multiply-subtract 5.84 (50%)
nb=8 时：估算 5.81 (33%)  multiply-subtract 11.68 (67%)
```

**multiply-subtract 现在与估算等价甚至更大**，且它是 d1 之后唯一没被动过的内核部分。
`subMulAt` 的 `@subWithOverflow` 双借位链在 ARM 上是否落成 `SBC` 链值得反汇编确认 ——
但这属于 d3 的工作，本轮不做。

阈值也值得单独一刀验证：`reciprocal_threshold = 3` 来自 qjs，
而本轮实测两段斜率差是 **17.56 − 11.65 = 5.91 ns/商位**（nb=4），
init 成本约 9–12 ns → 盈亏平衡点约在 **2 个商位**（`9.3 / 5.91 ≈ 1.6`），
**低于当前阈值 3**。也就是说 `m = 2`（3 个商位）可能已经该启用 reciprocal 了。
⚠️ 这同样是外推，需要独立 one-cut 验证。

## 7. 限制

- 只测了 shift = 0 的操作数；
- eligible 段的截距是从商位 5..17 外推到 0，**不能用它减出 reciprocal init 的成本**（§2.5）；
- direct-core 与 JS 层的分配器占比差异已说明，未归一到同一分配器；
- §5 的 JS 侧收益推理与 §6 的阈值盈亏平衡点**都是外推，不是测量**；
- `mod` 与 `div` 的斜率/截距未分别拟合（两者时间在所有形态上差 ≤3%）；
- arena churn 的观察来自符号占比，**未直接计数 arena 的创建/销毁次数**。
