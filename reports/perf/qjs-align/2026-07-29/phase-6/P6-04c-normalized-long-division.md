## 2. 机制与一处**刻意不照抄 qjs** 的地方

归一化除数使其最高 limb 高位置 1，然后每步产出一个商 limb：
由前导 numerator limbs 估算 → 用第二个除数 limb 修正 → multiply-subtract →
罕见溢出时 add-back。对应 qjs `js_bigint_divrem` + `mp_divnorm`（quickjs.c:11893-11976）。

⚠️ **没有照抄「最高 quotient limb 只可能是 0 或 1」那一支。**
qjs 的 `JSBigInt` 是带符号扩展的二补码，正数在最高位为 1 时会保留额外符号 limb，
所以它的最高商 limb 只能是 0 或 1；zjs 是规范化 sign-magnitude，
**最高商 limb 可以是任意 `u64`**。对齐的是 normalized limb-division 机制，
不是另一种表示带来的特例。

### 全程没有收缩 realloc

两个结果都在分配前就知道确切长度：

- **商**：最高位商位非零，当且仅当分子的前 `nb` 个 limb ≥ 除数
  （`compareAbsParts(lhs.limbs[m..na], rhs.limbs) != .lt`），`lhs < rhs` 已由调用者早退，
  所以长度至少 1；
- **余数**：先用只读的 `unshiftedLimbAt` 从高到低量出去掉归一化位移后的长度，
  再按该长度分配并填充。**零余数不分配。**

因此不需要 `normalize`，也就不存在 `ad6bd639` 修掉的那种所有权窗口。

`u` / `v` 两块 scratch 保持**两次独立分配**（不合并），
让分配拓扑可读、也让 OOM sweep 能逐个失败 —— 合并留给 P6-04d。

| `8×4` | 512 | P0 → P1 | 512 → **0** | 254 → **0** | 1278 → **6** |
| `16×8` | 1024 | P0 → P1 | 1024 → **0** | 510 → **0** | 2554 → **6** |

- **`mod-size-2x1` 是唯一 16 个组合全部 > 1.0 的**（区间下界 1.0216），
  幅度 +3.5%，**绝对量 1.5 ns**；
- `div-size-1x1` / `div-size-2x1` / `mod-size-1x1` 的区间都跨过 1.0，是噪声量级；

原因几乎可以肯定是代码布局：`divRemAbsAlloc` 从「两个分支 + 一个内联的逐 bit 循环」
变成「两个分支 + 两个 noinline 调用」，dispatcher 的 codegen 整体移位。
每次操作 1.5 ns，落在最小的形态上。

**未追。** 理由是投入产出：为 1.5 ns 再跑一轮 4 实例构建 + 测量，
与本刀 28x–272x 的量级不成比例；P6-04d 若合并 scratch 会再次改动这个 dispatcher，
届时应重测。**但门槛确实未达，不作粉饰。**

## 6. 正确性

### 6.1 定向向量（永久固化）

`normalized long division handles every quotient-estimate correction`：
每条向量都是**先给估算循环加事件计数器、随机搜索到触发输入、再把输入固化**
得到的；**计数器不在合入代码里**。

| 事件 | 来源 | 说明 |
|---|---|---|
| qhat 修正 ×1（两条） | 随机搜索 | 第二 limb correction 走一次 |
| qhat 修正 ×2、×3 | 随机搜索 | 单个商位上连续修正 |
| **add-back（三条）** | **定向搜索** | 随机差分**够不到**：概率约 2/2⁶⁴，且需要 ≥3 个除数 limb 才能让两 limb 修正漏掉 |
| **clamped estimate** | **手工构造** | 需要窗口最高 limb 恰等于除数最高 limb。构造法：分子的最高两个 limb 组成一个小于除数但与其共享最高 limb 的值，于是第一个商位为 0、把它原样留给下一步 |

四种符号组合逐条跑，验证 `q*b+r == a`、`|r| < |b|`、余数符号、结果无前导零 limb。

### 6.3 OOM

`multi-limb division survives a failure at every allocation point`（`ad6bd639` 引入，本刀继承）：
逐个失败每一个分配点 × 四种符号组合，每次必须**要么给出正确结果、要么 `OutOfMemory`**，
且事后 `live == 0`、**调用者的操作数 limbs 逐字节未被修改**；
另有一个模式让**每一次收缩 realloc 都失败**（同时拒绝 remap 与 alloc-and-copy 回退），
之后运行时仍可继续正常除法。

## 7. 一处需要更正的既往表述

P6-04b 的档案把 `divRemAbsAlloc` 的 `normalize` 所有权问题记为
「既有 double free，`test-oom` 未覆盖」。**这个表述过强。**
用计数器实测：那两次尾部 `normalize` 在 **2001 次除法中收缩 0 次** ——
`subAbsAlloc` 每轮都已把余数归一化，`setBit` 也让商的最高 limb 非零，
所以失败分支是死的，**双重释放不可达**。
`ad6bd639` 修的是**不成立的所有权模式**，不是活的缺陷；
随之加入的 fail-index sweep 的价值是**向前的 OOM 合同**，不是回归测试。
（`P6-04b-single-limb-division.md` §6 与 `P6-04b-results.json` 应按此理解。）

## 8. 限制

- **单 limb 最小形态的 1.6–3.5% 回退未追**（§5），门槛未达；
- `u` / `v` 仍是两次独立 scratch 分配，未合并（按设计留给 P6-04d）；
- 第一版**没有** reciprocal 预计算、Burnikel–Ziegler、Newton reciprocal、
  quotient/remainder FAM、combined scratch —— 全部按 PRD 排除；
- `div_8x4` 仍是 qjs 的 **3.20x**，第二阶段目标只在 `16x8`(1.60x) 与 `mod_8x4`(1.87x) 达成；
- 定向向量的事件触发是**加计数器时验证的**，合入代码里没有计数器，
  所以测试本身不能断言「这条向量确实走了 add-back」——它断言的是结果正确；
- `pow` 未测（它反复调用 `mulAlloc`，与除法无关）。
