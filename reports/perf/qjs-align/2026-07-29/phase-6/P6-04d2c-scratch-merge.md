## 1. 机制

`u` 与 `v` 生命周期完全相同（循环前建、读完余数即死），
一个 `[u][v]` 块替代两次分配：

```zig
const u_len = na + 1;
const scratch = try allocator.alloc(Limb, u_len + nb);
defer allocator.free(scratch);
const u = scratch[0..u_len];
const v = scratch[u_len..];
```

**顺序按 PRD 要求保持 `[u][v]`**，与原先两次分配的逻辑顺序一致，
使 multiply-subtract 的窗口、两次拷贝、unshift 看到的相对布局都不变。

### alias 防护（PRD 指出的最大风险）

合并后 `u` 与 `v` 出自同一分配，**相邻但不重叠**。
每个 helper 都把 `u` 的窗口与 `v` 当作两个独立切片；
`subMulAt(window, v, qhat)` 的窗口最大到 `u[na+1]`，正好是 `u` 末端 = `v` 起点。
因此加了断言把这条缝钉住：

```zig
std.debug.assert(v.len == nb);
std.debug.assert(@intFromPtr(u.ptr) + u.len * @sizeOf(Limb) == @intFromPtr(v.ptr));
```

**未做**：scratch arena、allocator cache、persistent temp buffer、FAM、thread-local workspace。

## 11.6 本轮暴露的一个更一般的问题（记录，不在本刀处理）

`SmallObjectSlab` 在某个 size class 的最后一个块被释放时立刻把 arena 还给 backing allocator。
对「每次操作分配再全部释放」的 workload，这导致**每次操作新建又销毁 arena**，
`addArena` 可以占到 **12.45%**（`div_4x4` merged）或 **9.45%**（`div_8x8` split）。

BigInt 除法只是撞上了它。这是 allocator 层的行为，不是 BigInt 的实现债，
但它解释了为什么 P6-04d0→d2.5 之间「分配次数减半而 JS 分配器占比不动」。
**若要根治，属于 allocator 层的独立课题**，不应再通过调整 BigInt 的分配拓扑去规避。
