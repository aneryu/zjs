## 0. 先更正一个数字

PRD 把这刀写成 `4 allocations → 3`，那是 **d2b 之前**的拓扑。
d2b 已经把多 limb 降到 **3**，所以这刀实际是 **3 → 2**（`.both` 路径是 4 → 3）。

## 1. 机制

`u` 与 `v` 生命周期完全相同（循环前建、读完余数即死），
一个 `[u][v]` 块替代两次分配：

```zig
const u_len = na + 1;
const scratch = try allocator.alloc(Limb, u_len + nb);
defer allocator.free(scratch);
const u = scratch[0..u_len];
const v = scratch[u_len..];
```

**顺序按 PRD 要求保持 `[u][v]`**，与原先两次分配的逻辑顺序一致，
使 multiply-subtract 的窗口、两次拷贝、unshift 看到的相对布局都不变。

### alias 防护（PRD 指出的最大风险）

合并后 `u` 与 `v` 出自同一分配，**相邻但不重叠**。
每个 helper 都把 `u` 的窗口与 `v` 当作两个独立切片；
`subMulAt(window, v, qhat)` 的窗口最大到 `u[na+1]`，正好是 `u` 末端 = `v` 起点。
因此加了断言把这条缝钉住：

```zig
std.debug.assert(v.len == nb);
std.debug.assert(@intFromPtr(u.ptr) + u.len * @sizeOf(Limb) == @intFromPtr(v.ptr));
```

**未做**：scratch arena、allocator cache、persistent temp buffer、FAM、thread-local workspace。

## 5. 机制已确认：**slab size class**

JS 层两侧 profile：

### `div_8x4`（−30.8%）：合并**去掉**了一个 churning class

| 符号 | P0 | P1 |
|---|---:|---:|
| `SmallObjectSlab.addArena` | **5.03%** | **消失** |
| `_int_malloc`（arena refill） | **4.19%** | **消失** |
| `allocAlignedBytesNoTrigger` | 10.32% | 5.68% |
| `divRemAbsNormalizedLong` | 33.24% | 47.99% |

### `div_16x8`（+8.8%）：合并**引入**了一个 churning class

| 符号 | P0 | P1 |
|---|---:|---:|
| `_int_malloc` | **无** | **2.58%** |
| `memcpy` | 无 | 2.65% |
| `allocAlignedBytesNoTrigger` | 4.53% | 3.86% |
| `divRemAbsNormalizedLong` | 66.45% | 61.97% |

`u` = 17 limbs、`v` = 8 limbs，合并块 25 limbs = 200 B ——
落进了运行时**不保持有块的 size class**，于是每次操作都要向 backing allocator 要 arena，
而 P0 的两个较小尺寸原本都能复用已有 arena。

**这正是 P6-04d2.5 预告的分叉**：

> 若 `u`+`v` 的合并块落进一个已被其他分配占用的 class → churn 不减；
> 若它让触及的 class 数从 3 降到 2 → 收益可能大于 7%。

实测两种情况**同时发生在不同形态上**。d2.5 的推理成立，但它只预见了单向。

## 9. 限制

- size class 的解释来自符号占比 + `addArena`/`_int_malloc` 的出现与消失，
  **未直接计数 arena 的创建次数**；
- **`24×8` 没有 JS case**，它在 JS 层的合并行为**未测** ——
  只有 direct-core（改善 1.1~1.8%）；
- 未尝试挑一个更友好的 size class（PRD 排除的 allocator-aware tuning）；
- 拓扑计数仍只覆盖 shift = 0 的操作数。
