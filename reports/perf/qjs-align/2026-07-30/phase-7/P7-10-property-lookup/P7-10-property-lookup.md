# P7-10：property lookup 归因与 `recordPropLookup` 偏差修正

- 日期：2026-07-30
- 起点：`perf/qjs-align-p7-property` @ `a5bbbe52`
- 对照引擎：pinned Bellard QuickJS `04be2460`
- 性质：剖析 + 一处 instrumentation 门控（见第 6 节，未合入集成分支）
- 数据产物：`P7-10-results.json`

## 1. 结论

### 偏差修正：**没有可测量的偏差，修正后的比值等于修正前的比值**

`recordPropLookup` 编译进二进制这件事，在属性 benchmark 上**测不出影响**。全部 4 个 P0→P1 组合的指令位移落在 **±0.244%** 以内，且符号在组合之间不一致；而同源两次冷缓存构建（P0-a vs P0-b）的**构建双稳**本身就达到 **2.014%** cycles，字节完全相同的两个二进制之间的**噪声地板**也有 **0.409%** cycles。**去插桩的效果比构建双稳和测量噪声都小，因此不能声称有效果。**

机制上这本来就是可预期的，事前也是这样预判并写下的：`prop_read_mono` 这类单态属性读的热路径是 `exec/tailcall_dispatch.zig:2977` 的 `qjsGetFieldFastSlot`，**根本不经过 `Object.getProperty`**；计数器只坐在冷的 `get_field_property` 尾上。按本战役既定的「用指令占比而非周期占比定收益上界」纪律，预期位移本就接近零，实测证实了这一点。

**因此此前任何引用过的 property 路径比值都不需要因插桩而修正。**

### 归因：**顶层惩罚是绑定访问，不是属性查找**

这是本条线的主结果，直接回答了立项时那个「顶层绑定访问和真正的 own-property lookup 是否被当前 benchmark 混在一起」的问题：**混在一起了，而且混进去的那一份几乎就是全部。**

| 形态 | 顶层 | 局部 | 顶层−局部 |
|---|---|---|---|
| **binding-only（完全不碰属性）** | 1.087 | 0.931 | **+0.155** |
| read | 1.046 | 0.889 | **+0.157** |
| write | 1.286 | 1.004 | +0.282 |

read 的顶层惩罚 **+0.157** 与完全不碰属性的 binding-only 惩罚 **+0.155** 在噪声内相等。**属性查找对顶层惩罚的贡献是零。**

### 属性读已达到或超过对齐；真正的残差在属性写

扣掉同形态 binding-only 之后的净成本：

| | 净 insn/迭代 qjs → zjs | insn 比 | 净 ns/迭代 qjs → zjs | 时间比 |
|---|---|---|---|---|
| read / 顶层 | 52.0 → 58.1 | 1.12 | 3.9 → 3.6 | **0.92** |
| read / 局部 | 52.1 → 58.0 | 1.11 | 3.4 → 2.6 | **0.77** |
| write / 顶层 | 180.0 → 258.7 | 1.44 | 10.1 → 15.3 | **1.52** |
| write / 局部 | 150.0 → 171.4 | 1.14 | 7.1 → 7.8 | **1.10** |

**own-property read 在时间上已经反超 qjs**（0.77–0.92），尽管指令多 11–12% —— 又一次出现本仓库反复见到的「指令多但时间不差甚至更好」的形态，zjs 侧 IPC 更高（read_local 6.30 vs 5.82）。**属性写才是真正的残差**，顶层写净时间比 1.52。

## 2. 方法

六个 case，每个 2 000 000 次迭代，形状除了要考察的那一维之外完全相同（同样的接收对象形状、同样的累加算术、同样的可观测校验和）：

```
read_toplevel / read_local          obj.x 读，obj 与 acc 分别是顶层绑定 / 函数局部
write_toplevel / write_local        obj.x = i; acc += obj.x
binding_toplevel / binding_local    acc += v，完全不碰属性
```

后两个是关键：**只有引入一个完全不碰属性的对照，才能把「顶层绑定访问」从「own-property lookup」里减出来。** 没有它，read 的 1.046 与 0.889 之差会被误读成属性查找的差异。六个 case 在两侧输出逐项一致。

采样：每配置 6 个样本（**偶数**，否则 ABBA 顺序不平衡，本战役已因此作废过两次头条数字），配置顺序在偶数样本上整体反转，`taskset -c 19`，全程持有独占主机锁，取中位数。同时记录 instructions 与 cycles —— 指令赢不等于时间赢。

**每侧两个冷缓存构建实例，全组合报告。** 这一条在本条线上是必需而非仪式：P1 侧两次构建**字节完全相同**（sha `c594f4d3…`），P0 侧两次构建**不同**（`4e919955…` / `92192ba5…`）。于是 P1-a 与 P1-b 的差异就是一把免费的噪声尺 —— 二进制完全一样，测出来的任何差都是测量噪声。

## 3. 三个量级必须放在一起看

| 来源 | insn | cycles |
|---|---|---|
| 噪声地板（P1-a vs P1-b，字节相同） | ≤0.010% | ≤0.409% |
| 构建双稳（P0-a vs P0-b，同源不同二进制） | ≤0.238% | **≤2.014%** |
| **去插桩效果（P0→P1，全 4 组合）** | **≤0.244%** | ≤2.286% |

去插桩的效果**没有从双稳里浮出来**。`write_local` 是最刺眼的例子：`p0-a/p1-a` 组合显示 +2.286% cycles，看起来像回退，但 `p0-b/p1-a` 只有 +0.226%，而 P0-a 与 P0-b 之间本身就差 −2.014% —— 这个 +2.286% 是布局彩票，不是插桩。**若只建一个实例、只看一个组合，本条线会得出一个完全错误的结论。**

## 4. 逐 case 绝对量

zjs 取 P1（两实例字节相同），每次迭代：

| case | qjs insn | zjs insn | insn 比 | qjs ns | zjs ns | 时间比 | qjs IPC | zjs IPC |
|---|---|---|---|---|---|---|---|---|
| `read_toplevel` | 324.4 | 349.3 | 1.077 | 15.8 | 16.5 | 1.046 | 5.26 | 5.42 |
| `read_local` | 294.4 | 283.3 | 0.962 | 13.0 | 11.5 | **0.889** | 5.82 | 6.30 |
| `write_toplevel` | 452.4 | 549.9 | 1.216 | 22.0 | 28.3 | **1.286** | 5.28 | 4.99 |
| `write_local` | 392.3 | 396.7 | 1.011 | 16.7 | 16.7 | 1.004 | 6.04 | 6.08 |
| `binding_toplevel` | 272.4 | 291.2 | 1.069 | 11.9 | 12.9 | 1.087 | 5.87 | 5.77 |
| `binding_local` | 242.3 | 225.3 | 0.930 | 9.6 | 8.9 | 0.931 | 6.50 | 6.49 |

`write_toplevel` 是唯一 IPC 反向的 case（zjs 4.99 vs qjs 5.28），与它 1.286 的时间比一致 —— 那里既多做指令又跑得更差，是本条线唯一同时在两个维度上落后的形态。

## 5. 与 P7-20 线索的关系

P7-20 交来的线索是：`prop_read_mono`（顶层绑定）1.234 而 same-runtime 的 `prop_read_mono_loop`（函数局部）0.874，候选归因为「顶层绑定访问而非属性查找」，但因跨层不可相减而只能登记为待查。

**本条线在单一层内证实了该候选归因，并给出了它此前缺的那个对照。** 顶层与局部的时间比之差在 read 上是 +0.157，而完全不碰属性的 binding-only 对照给出 +0.155 —— 两者相等意味着差异全部来自绑定访问。P7-20 当时无法排除的「两个 case 迭代次数与工作量也不同」这一混淆，在这里通过同层、同迭代数、同校验和被消除。

P7-20 记录的那条不一致（`global_write_loop` same-runtime 只有 1.039，与「顶层绑定更贵」的方向相反）**本条线没有解决**：那是 strict 模式的顶层写，形状与这里的 `write_toplevel` 不同，留作未决。

## 6. 关于那处 `src/` 改动

`src/core/object.zig` 的两处 `profile.recordPropLookup(self.isGlobal())`（`hasProperty` / `getProperty`）**原本没有 comptime 门控**，而同类计数器在 `core/value.zig`、`exec/vm_profile.zig`、`exec/vm_call.zig` 中**早已**门控在 `build_options.zjs_enable_opcode_profile`（`build.zig:15`，默认 `false`）。本条线按同一模式补上门控，因此这是**补回既有约定**而不是新增开关。

顺带消掉一处无条件开销：`self.isGlobal()` 作为实参，在 `active_profile` 的 null 检查**之前**被无条件求值，而 `active_profile` 是 `threadlocal`（aarch64 上是一段 TLS 访问序列）。

**但按本条线自己的测量，这处改动没有可测量的性能收益**（见第 3 节）。它的正当性是一致性与死代码消除，不是性能。

**裁决（2026-07-30）：这 9 行不合入。** 本条线只交付报告与 benchmark cases，`src/core/object.zig` 已还原到 `a5bbbe52` 原样。理由是它本来只为 P0/P1 偏差实验服务，而实验结论恰恰是偏差不可测；没有生产收益就不应在仓库里留下一个新的实验控制面。P0/P1 二进制的构建方式与 sha256 已完整记录在 `P7-10-results.json`，任何人可以据此重建这次实验。

若日后要单独做这项清理，它必须满足：不新增任何 build option、只使用仓库已有的 profiling 编译期契约、profile-enabled 行为逐项不变、默认二进制确实减少死代码。届时应作为独立的非性能提交 `refactor(profile): compile out disabled property lookup recording` 提出，**不得与本归因提交混合**。

一处不宜过度解读的观察：P1 侧两次冷缓存构建字节相同而 P0 侧不同，可能意味着门控消掉了一处 codegen 不稳定性 —— 但 n=2，**不足以支撑「消除了双稳」这个说法**，此处只作记录。

## 7. 本线未做的事

- **未**回答属性写为什么慢（顶层净时间比 1.52）。本条线只定位到「残差在写不在读」，没有进入 shape/descriptor/写屏障层面归因。这是下一条属性线的入口，不是本线的结论。
- **未**解释 `global_write_loop` 1.039 与本线 `write_toplevel` 1.286 的方向不一致（见第 5 节）。
- **未**测量多态与原型链形态。`prop_read_poly3` 1.024 与 `proto_read` 0.997 在 Phase 6 收口时已接近或反超，本线没有重测。
- `write` 形态的差分口径不如 `read` 干净：`obj.x = i; acc += obj.x` 每次迭代含一次属性写加一次属性读，而 binding-only 基线只有一次绑定读，所以 write 的「净成本」里混着一次属性读。read 的差分没有这个问题。**write 的净值应作为上界读，不是精确值。**
