# full-every-2 sticky major 实验臂:机制、三前提与定价

分支 `gc/opus-every2`,base `f4ea32f1`。本文只交付**臂的建设与定价数据**;
是否采纳归 owner 裁,cycles 裁决归 driver 安静窗口。记账在
`docs/splay-account-2026-08-28.md`,本文不动那份。

---

## 0. 结论先行

三前提已齐备并各有证据,臂可用一个 build 选项 + 一个环境变量驱动,四门全绿。

**但定价结论是否定的:臂被一个更简单的对照严格支配。**

在**同一个峰值内存点**(splay,账面 peak 384 MB / RSS 420 MB):

| | 指令数 | vs base | peak | major |
|---|---:|---:|---:|---:|
| 臂开(full-every-2) | 31.994 G | **−3.60%** | 384.8 MB | 24 (12 full + 12 sticky) |
| 臂关 + 单纯提高阈值 | 31.073 G | **−6.37%** | 384.0 MB | 8 (全 full) |

同样的 +161 MB,**「少收几次」买到的收益是 sticky 机制的 1.77 倍**;而且只花
+37 MB(260 MB 点)的纯阈值调整就已经 −4.72%,超过臂花 +161 MB 拿到的 −3.60%。
sticky 标记路径、独立阈值、fresh oracle 这一整套机器,在 splay 上换不到任何
「阈值旋钮换不到」的东西。详见 §5.4。

EB 上臂没有被支配(−0.67% vs 等 peak 阈值的 −0.60%,且 RSS 明显更省),但效应
只有 spread 的 3 倍,且 EB 的 major 便宜到砍掉 95% 也只值 −0.41% ⇒ 无裁决力(§5.5)。
按 §4o「splay 承担全部剩余差距」,权重在 splay。

正确性侧是干净的:oracle 在 splay + EB 上共 **6,700 余次 sticky 轮**审计中
**precise 违例 0**,注入 1 个漏标即报 503 例并 fail-closed。**未发现 sticky 路径的
正确性缺陷。**

## 1. 臂的机制

隔一次 full major 做一次 sticky(根 + 全脏)major。

- **full scope**:`collector.clearMarks()` 后从根重新展开全堆(现行行为)。
- **sticky scope**:**不清标记**。老对象仍带着上一次 full 留下的标记,因此
  普通的根染色会在它们身上短路、不再展开其子节点。臂显式补上这一步:把
  remembered set(old→young 屏障记下的「全脏」老 owner)快照出来,逐个
  `traceHeader` 强制展开,young 目标由此进入持久 frontier;随后照常
  seedRoots + seedConservativeRoots。

买的是被跳过的那次 full 的**重复展开**。lane-a 已实测这只占 full 的 31%
(sticky 仍需展开 full 的 68.9%,因为每个间隔约 553K 个**新可达** header 顶替旧
payload,那是首次标记、不可免)。所以预期上界就是 ~0.25G cycles,不是 1.0G。

代价是**浮动垃圾**:被跳过的那次 full 本该回收的死对象,因为标记还在,活到下一轮。

### 相关提交

`095e0268 gc: add gated full-every-2 sticky major experiment` 已在 base 的祖先里
(经 `ba2f76ac` 合入)。本轮在其之上补齐。

**095e0268 已有的**:build 选项 + `sticky_major_enabled` comptime 常量 + 非法组合

**本轮补齐的**:

1. **运行期开关** `ZJS_GC_STICKY_MAJOR`(§2.1)——让 A/B 落在**同一个二进制**上。
2. **oracle 注入旋钮** `ZJS_GC_STICKY_INJECT_SKIP`(§4.3)——让注入验证能在
   **目标构建形态**(ReleaseFast 臂开)里做,而不是只在 Debug 单测里。
3. **oracle 的全 scope 对照** `ZJS_GC_VERIFY_MAJOR_ALL`(§4.2)——这是本轮最关键的

   **`max_ordinary_threshold`**——前提 #2 的运行期证据(§3)。
6. 两个新单测:运行期开关的双向语义、注入旋钮的红臂。

## 2. 前提 #1:trace 门控

形态照抄既有 `-Dzjs_experimental_gc_sticky_major` 三层门控:

- `build.zig`:`b.option(bool, "zjs_experimental_gc_sticky_major", ...)`,
  `orelse false`;与非 `trace_stw` 组合时 `std.debug.print` + `process.exit(1)`。
- `src/core/gc.zig`:
  `pub const sticky_major_enabled: bool = trace_stw_enabled and build_options.zjs_experimental_gc_sticky_major;`
- 所有状态字段、统计、env 解析、调度分支都在 `if (comptime sticky_major_enabled)`
  之后;`StickyMajorState` 在关闭时是 `void`。

### 证据:rc `.text` 逐字节不变

判据是候选构建**两次**复现 base sha。

| 构建 | `.text` sha256(前 16) |
|---|---|
| base `f4ea32f1` rc ReleaseFast | `4ae2685705e87002` |
| 候选 rc ReleaseFast(第 1 次) | `4ae2685705e87002` |
| 候选 rc ReleaseFast(第 2 次,独立 cache-dir) | `4ae2685705e87002` |

### 2.1 运行期开关(本轮补)

`ZJS_GC_STICKY_MAJOR=0` 把每一轮自定步 cycle 压回 full scope。存在的理由是
**定价必须在一个二进制里做**:两个二进制的 A/B 会把布局差异、额外状态字段、
额外分支一并算进被测效应里。

开关是**双向**的:关掉时 `stickyMajorFullPressureExceeded` 也返回 false。否则
「关臂」一侧仍会带着第二个触发器,收得比普通策略更勤——那不是一个可用的参照臂。
单测 `the sticky arm's runtime switch keeps one binary honest on both sides` 钉住
这两条。

**参照臂保真度实测**(同一负载,arm-off 的臂二进制 vs 默认 trace 二进制):

| 负载 | 默认 trace 二进制 | 臂二进制 arm=off | 差 |
|---|---:|---:|---:|
| splay | 33,257,714,558 | 33,225,502,434 | −0.097% |
| earley-boyer | 475,059,823,292 | 474,718,787,706 | −0.072% |

均落在同负载 spread(0.16–0.38%)之内 ⇒ 同二进制 A/B 的关臂侧是默认行为的忠实参照。

## 3. 前提 #2:独立 full-pressure 阈值

sticky 轮的浮动垃圾会抬高结算存活集 S。普通阈值在每次 collection 之后按
`max(1.75×S, S+headroom)` 重置——**用的是被 sticky 污染过的 S**,于是逐轮上涨。

实现:第二条阈值,基线**只在 full 之后**变。full 结算时记下
`S_full` 与当时的普通阈值,取 `window = 普通阈值 − S_full`,置

```
full_pressure_threshold = S_full + 2 × window
```

给两份「首个 full 后的分配窗口」:一份走到 sticky 轮,一份走到强制 full。
`stickyMajorFullPressureExceeded()` 越线即在 `prepareIncrementalMajorScope`
里强制 full scope,并在 `pollGC` 里把它并进 `over_collection_threshold`。
sticky 轮结算(`noteIncrementalCollectionSettled` 的 `.sticky` 分支)**不触碰**
这两个字段。

不完整 arena 的 full 不算基线:此时 collector 有意保留未标记对象而不清扫,
old→old 写可能复活其中之一,而分代 remembered set 有意不记这条边 ⇒
`full_baseline_valid = false`,退回全 full。(095e0268 已有,单测
`sticky major rejects an incomplete full as its baseline` 钉住。)

### 证据:棘轮是真的,而且盖子在承力

运行期读数(splay,臂开,`--gc-stats`):

```
last-full settled          133,781,874   (S_full ≈ 127.6 MB)
full-pressure threshold    334,454,684   (= S_full + 2×window, window ≈ 100.3 MB)
max ordinary threshold     403,149,435   ← 被 sticky 污染的普通阈值实际爬到的高度
pressure-forced full       10 / 12
```

**普通阈值确实棘轮到 403.1 MB,比独立盖子高出 68.7 MB。**12 次 full 里有 **10 次**
是被这条独立阈值强制的,而不是靠 every-2 交替。也就是说:

- 前提 #2 不是纸面防御,它是这个臂里**实际排班的主力**;
- 没有它,「隔一次」会退化成「隔很多次」,浮动垃圾无界增长。

EB 同向:`max ordinary threshold` 25.05 MB vs pressure threshold ≈ 18.1 MB。

结构证据由单测提供:`sticky major alternates with full ...` 在一次 sticky cycle
前后 `expectEqualDeep(full_baseline, rt.gc.stickyMajorFullBaseline())` ——
sticky 轮一个字节都没动到基线。

## 4. 前提 #3:fresh-trace shadow oracle

### 4.1 机制

`ZJS_GC_VERIFY_STICKY_MAJOR=1`。在 `finishIncrementalCycle` 里,remark 完成、
`major_marking_active` 落下之前、任何 weak 状态或对象存储被改动之前:

1. `computeFullReachable` 保存现有标记 → `clearMarks` → 从根重新全量 trace
   (precise,然后 conservative)→ 记下可达集 → 恢复标记。
   它在诊断期间压掉 marking flag,避免自己的根遍历往被审计的生产队列里黑发布。
2. `verifyStickyCondemnation` 遍历全堆,取**这次 sticky 即将定罪的确切集合**
   (未标记且非 pinned),与 fresh 可达集求交。
3. 交集非空 ⇒ 记账 + 打印 + `error.PayloadMarkFailed`,cycle 中止并安排 full 修复。

方向正确:sticky 允许**多留**(浮动垃圾,本来就是它的代价),oracle 只抓**少留**。

### 4.2 本轮补的两件事,以及为什么必须补

第一轮跑绿臂就出事:12 次 sticky 审计里报出 **1 例违例**。看上去是抓到了缺陷。

打开明细,它是 `conservative_only` —— fresh trace **只**经由保守栈候选够到它。
而 `computeFullReachable` 自己的合同里早就写着:oracle 与被审计的 cycle
**跑在不同的 native frame 上**,残留指针可以只存在于两次扫描中的一次
(minor verifier 一直为此把这一类单列)。

于是我做了两件事:

**(a) 违例按来源分离**,fail-closed 收窄到 `precise`。conservative-only 仍然计数、
仍然打印,但不再中止健康的 cycle。

**(b) 加全 scope 对照** `ZJS_GC_VERIFY_MAJOR_ALL=1`:把同一台 oracle 也架到
**full scope** 的 cycle 上。full scope 从清空的标记重新导出一切,**按构造不可能
少标**——所以它报出来的任何东西,就是这台仪器自己的噪声地板。

没有 (b),那个「1」读不出是缺陷还是噪声。有了 (b),读数如下(splay,每次运行
29 次 full 审计 / 12 次 sticky 审计):

| 臂 | 审计次数 | precise 违例 | conservative-only 违例 |
|---|---|---:|---:|
| **对照:关臂,全 full** (5 次运行) | full 29 ×5 | **0, 0, 0, 0, 0** | 9, 10, 9, 8, 298 |
| **处理:开臂,full+sticky** (5 次运行) | full 12 + sticky 12,×5 | **0, 0, 0, 0, 0** | 4, 101, 3, 4, 4 |

EB(每次运行数千轮):

| 臂 | 审计次数 | precise | conservative-only |
|---|---|---:|---:|
| 对照:关臂 (3 次运行) | full 5224 / 5213 / 5228 | **0 / 0 / 0** | 124,542 / 138,300 / 123,443 |
| 处理:开臂 (3 次运行) | full+sticky 各 2224/2178/2206 | **0 / 0 / 0** | 101,336 / 91,841 / 111,385 |

**读法**:conservative-only 在**不可能出错的对照臂上出现得同样多甚至更多**
(EB 每次审计 23.8 例 vs 处理臂 22.8 例)⇒ 它是仪器噪声,不是机制缺陷。
precise 一列在 splay + EB、两个臂、十余次运行、**共 6,700 余次 sticky 轮审计**里
**恒为 0**。

### 4.3 注入验证(目标构建形态)

`ZJS_GC_STICKY_INJECT_SKIP=N`:sticky 展开时**故意跳过**前 N 个 remembered owner。
这正是「丢了一次写屏障」的形状——老 owner 不被展开,只有它够得到的 young 子节点
就会被定罪。默认 0。

在 **ReleaseFast + 臂开**(即定价用的同一构建形态)下跑 splay:

| 注入 | precise 违例 | conservative-only | oracle 行为 |
|---|---:|---:|---|
| **0**(绿臂) | **0** | 0–1 | 通过,不中止 |
| **1**(跳 1 个 owner) | **503** | 0 | 开火,`error.PayloadMarkFailed`,cycle 中止 |
| **8** | **13,821** | 1 | 开火,中止 |

`VERIFY-STICKY condemned-but-reachable scope=sticky source=precise kind=object`
(以及 `kind=function_bytecode`)。

**只跳 1 个 owner 就产生 503 例 precise 违例**,与绿臂的 0 之间没有任何重叠区 ⇒
oracle 对它要抓的那类故障是灵敏的,而且是在目标构建形态里证明的。

单测侧另有两条红臂:`... its fresh oracle rejects a missing remembered owner`
(用 `generation.forget` 制造缺屏障)与本轮新增的
`the sticky injection knob reproduces a lost barrier and the oracle refuses it`。

### 4.4 正确性结论

**未发现 sticky 路径的正确性缺陷。** 因此继续定价。

## 5. 定价

### 5.1 口径

- 二进制:`zig build zjs -Doptimize=ReleaseFast -Dzjs_experimental_gc=trace_stw
  -Dzjs_experimental_gc_sticky_major=true`,ReleaseFast,编译 `taskset -c 0-14`。
- 臂开/臂关 = **同一二进制**,`ZJS_GC_STICKY_MAJOR=1|0`。
- 测量核 `taskset -c 19`(idle 100%),**ABBA 交错 ×3 轮 = 每臂 6 样本**,取中位数。
- 指令数用 `perf stat -e instructions`,匹配 `pmuv3_1/instructions`
  (`armv8_pmuv3_0` 恒 `<not counted>`)。
- **指令数与内存分两趟采**:`--gc-stats` 自带全堆 census 走查,会污染指令数。
- **wall / cycles 不在本文作裁决**(归 driver 安静窗口)。

**与 lane-a 预测的对照**:预测 `+105MB peak 换 ~0.25G cycles`。实测峰值代价是
**+161 MiB 账面 / +169 MiB RSS**,比预测高 **60%**。指令侧 −3.545%(cycles 归 driver)。

### 5.3 混淆项:臂不只是「换了标记方式」,它还**少收了几次**

splay 的 major 从 29 掉到 24,EB 从 5196 掉到 4426。原因是 sticky 轮留下的浮动垃圾
抬高了结算 S,普通阈值随之重置得更高 ⇒ 下一次 collection 来得更晚。

所以 −3.545% 是**两件事的复合**:(a) 12 次 cycle 省掉了 clear + 重复展开,
(b) 总共少跑 5 次 cycle。这份数据**无法把两者分开**。

而这正引出下面那个必须做的对照。

### 5.4 决定性对照:同样的内存,单纯「少收几次」买到多少?

如果 +161 MB 的峰值预算就摆在桌上,最笨的花法是**直接把收集阈值调高**——不加
任何机制。用 `ZJS_GC_MIN_THRESHOLD`(现成的诊断旋钮)把臂关一侧的阈值抬到
各个高度,与臂开点作等内存比较。

splay,6 样本交错(ABBA ×3),`taskset -c 19`:

| 点 | 指令数(中位) | spread | vs base | major | 账面 peak | maxRSS |
|---|---:|---:|---:|---:|---:|---:|
| 臂关 base | 33.189 G | 0.160% | — | 29 (29F) | 223.3 MB | 251.1 MB |
| **臂开 every-2** | **31.994 G** | 0.350% | **−3.60%** | 24 (12F+12S) | **384.8 MB** | **420.4 MB** |
| 臂关 min-thr 260M | 31.621 G | 0.281% | **−4.72%** | 14 (14F) | 260.0 MB | 288.0 MB |
| 臂关 min-thr 300M | 31.241 G | 0.375% | **−5.87%** | 11 (11F) | 300.0 MB | 329.1 MB |
| 臂关 min-thr 340M | 30.975 G | 0.341% | **−6.67%** | 9 (9F) | 340.0 MB | 371.1 MB |
| **臂关 min-thr 384M** | **31.073 G** | 0.345% | **−6.37%** | 8 (8F) | **384.0 MB** | **418.5 MB** |
| 臂关 min-thr 460M | 30.612 G | 0.287% | −7.76% | 6 (6F) | 460.0 MB | 498.1 MB |

**在臂自己的内存点上(384 MB peak / ~419 MB RSS),不加任何机制的纯阈值调整
拿到 −6.37%,而臂只拿到 −3.60%。臂用同样的内存买到了 56% 的收益。**

更难堪的是 260 MB 那一行:只花 **+37 MB**(臂花的 23%)就已经 −4.72%,
**超过臂花 +161 MB 拿到的 −3.60%**。

也就是说 §5.3 的分解其实有答案了:臂的收益里,「少收几次」那部分不但是主要的,
而且臂拿这部分拿得**比直接调阈值更贵**——因为它为了少收几次,还得替 12 次
sticky 轮付出「不清标记但仍要展开全脏集」的成本,以及浮动垃圾撑大的堆上每次
标记/清扫更差的局部性。

> ⚠️ 测量陷阱记录:这个对照我第一次「复验」时读出了相反结论(对照臂与臂开
> 完全同值)。原因是 **zsh 对未加引号的参数展开不做分词**,
> `ev="A=0 B=1"; env $ev cmd` 传的是**一个**名为 A、值为 `0 B=1` 的变量 ⇒
> `ZJS_GC_STICKY_MAJOR` 被设成非 "0" 字符串 ⇒ 「对照臂」其实臂是开着的。
> 上表由 Python 以 dict 传 env 重跑,并与首轮单样本扫描一致。

| **臂关 min-thr 24M** | **471.838 G** | 0.155% | **−0.60%** | 144 (144F) | **24.00 MB** | 75.8 MB |
| 臂关 min-thr 32M | 472.260 G | 0.218% | −0.51% | 104 (104F) | 32.00 MB | 100.9 MB |

**EB 上臂没有被支配**:等账面 peak(24 MB)时臂 −0.67% vs 阈值 −0.60%,基本平手;
而**进程 RSS 上臂明显更省**(41.5 MB vs 75.8 MB)——粗暴抬阈值会让 block heap
提交一大片,sticky 的浮动垃圾则复用已提交的块。

但两点让这个胜利不值钱:

1. **量级 −0.67%,而 spread 0.16–0.26%**,只有 3 倍分辨率;
2. EB 的 major 便宜到几乎不要钱——5231 次砍到 271 次(20 倍)只换来 −0.41%。
   EB 的时间根本不在 major 调度上,所以这个基准对本机制没有裁决力。

按 §4o,**splay 一个基准承担了全部剩余的差距**,其余五个已在线内。所以裁决权重
应当压在 §5.4 的 splay 对照上,那里的结论是明确的支配。

## 7. 交给 owner 的话

臂建好了,三前提齐备,正确性干净。但**我不建议采纳**,理由不是它没效果,而是
**它在自己的内存点上被一个零机制的对照击败**(§5.4):同样 +161 MB,
纯阈值调整 −6.37% vs 臂 −3.60%。

如果 owner 的问题是「愿不愿意为 splay 花 +161 MB 峰值」,那么答案与 sticky
无关——该花就直接调 growth/阈值,不必引入 sticky 标记语义、独立阈值、
浮动垃圾会计和一台 oracle。

唯一对臂有利的读数是 EB 的 RSS(§5.5):等账面 peak 时臂 41.5 MB vs 阈值 75.8 MB。
如果 owner 关心的是**提交内存而非账面 peak**,这一条值得单独立案——但它是
「浮动垃圾复用已提交块 vs 抬阈值新提交块」的分配器性质,和 sticky 标记省下的
那 31% 重复展开无关,可以用比整套 sticky 便宜得多的方式去拿。

如果 owner 仍想保留这条线,值得先答的问题是:**在阈值固定的前提下**
(即强制臂开与臂关跑出相同的 major 次数与相同的 peak),sticky 每轮省下的
那 31% 重复展开还剩多少?本轮数据答不了这个问题,因为臂会自己把阈值推高。
那需要给 sticky 轮的结算加一条「按 S_full 而非 S_sticky 重置普通阈值」的
规则——**那是个新机制,不在本次 conditional GO 的授权范围内**,故未做。

## 附:复现命令

```bash
# 臂二进制
taskset -c 0-14 zig build zjs -Doptimize=ReleaseFast \
    -Dzjs_experimental_gc=trace_stw -Dzjs_experimental_gc_sticky_major=true

# 定价(同二进制 A/B,ABBA ×3)
.scratch/price.sh ./.scratch/zjs-arm 19 3 .scratch/price

# oracle 绿臂 + 全 scope 对照
ZJS_GC_ARENA_AUDIT=1 ZJS_GC_VERIFY_MAJOR_ALL=1 \
    taskset -c 19 ./.scratch/zjs-arm --gc-stats /tmp/gcgap-fixed/splay.js
# 同上加 ZJS_GC_STICKY_MAJOR=0 即为「全 full」噪声地板对照

# oracle 注入
ZJS_GC_ARENA_AUDIT=1 ZJS_GC_VERIFY_STICKY_MAJOR=1 ZJS_GC_STICKY_INJECT_SKIP=1 \
    taskset -c 19 ./.scratch/zjs-arm --gc-stats /tmp/gcgap-fixed/splay.js
```

环境变量总表(全部只在臂构建里解析):

| 变量 | 默认 | 作用 |
|---|---|---|
| `ZJS_GC_STICKY_MAJOR` | 1(臂构建内) | 0 = 全部退回 full scope,且关掉第二阈值 |
| `ZJS_GC_VERIFY_STICKY_MAJOR` | 0 | sticky 轮跑 fresh-trace oracle |
| `ZJS_GC_VERIFY_MAJOR_ALL` | 0 | full 轮也跑 oracle(噪声地板对照) |
| `ZJS_GC_STICKY_INJECT_SKIP` | 0 | 跳过前 N 个 remembered owner(注入故障) |
