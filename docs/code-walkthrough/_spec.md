# 源码逐函数讲解：写作规范

本系列面向要把 zjs **读到每一个函数实现** 的人。权威仍是源码与 ECMA-262；本文只规定分册怎么写、怎么核对覆盖。

## 范围

覆盖仓库里的生产 Zig 源码与构建/工具入口（测试代码不纳入本轮验收）：

- `src/` 的非测试实现（含方法、`inline fn`、`noinline fn`、`export fn`、私有函数）；测试块、测试文件及仅供测试的辅助函数不要求补充讲解
- `build.zig` 与 `build/*.zig`
- 引擎相关的 `tools/`（gates、文档/lint 入口）；不逐行讲 `test262/` 子模块、不讲 `.scratch/` 实验树、不讲 `zig-out/`

函数清单权威文件：[`_inventory.tsv`](_inventory.tsv)（从当前树扫描，含行号）。分册必须覆盖自己负责的非测试实现在清单里的**每一行**；测试辅助项保留用于历史对账，不属于本轮补写要求。

零函数文件（只有类型、error set、re-export）也必须讲：文件职责、每个 `pub const` / 结构体字段 / error 成员的含义。

## 每条函数怎么写

标题格式：

```
### `Type.fnName` (`src/path/file.zig:LINE`)
```

顶层函数没有 `Type.` 前缀。同一名字因嵌套类型重复时，标题必须带类型路径，例如 `` `JSContext.eval` ``、`` `ParseState.emit` ``。

正文固定四段，缺省写「无」而不是省略：

- **签名**：可见性、`inline`/`export`、参数类型、返回/error set。
- **作用**：一句话，说它在引擎里干什么，不复述函数名。
- **实现**：控制流、关键分支、与 QuickJS / ECMA-262 的对应点（有 `// quickjs.c:N` 或 spec 注释就引用）、热路径与冷路径、不变量。必须根据源码写，禁止臆造。
- **所有权 / 错误 / 调用**：谁分配谁释放；GC 根；error 如何变成 JS 异常；非显然的调用方与被调用方。

getter / 薄包装也不能跳过，可以短写，但仍要有这四段。

## 类型与数据

在函数之前先讲文件级类型：

- `extern struct` / `packed struct` 的字段布局与 ABI 钉
- tag、enum、error set
- 表驱动数据（opcode 表、atom 表、unicode 表）说明生成方式与消费点，不必把每个常数字面量抄一遍

## 语言与风格

- 中文正文，标识符、文件名、opcode、error 名保持源码原文。
- 先讲「这段代码做什么」，再讲「怎么做」。
- 不写营销句，不写「TODO 以后补」。覆盖缺口必须列在文末「覆盖核对」。
- 不修改 `src/`、`build/`、测试；本系列只写 `docs/code-walkthrough/`。

## 分册体积

单文件源码超过约 4000 行或函数超过约 200 个时，拆成 `NN-name.md` + `NN-name-*.md`，并在主文件给子文件目录。

## 覆盖核对（强制）

每篇文末：

```
## 覆盖核对

- 清单函数数: N
- 本文标题覆盖: M
- 未覆盖: 无 | 列出 `file:line name`
```

核对命令（指定待核查的源码文件与文档）：

```sh
python3 docs/code-walkthrough/_check_coverage.py \
  --docs 'docs/code-walkthrough/04-*.md' src/compiler/labels.zig
```

检查器先核对当前源码与清单，再以「源文件 + 实际声明行 + 函数名」匹配函数标题。类型方法允许带限定前缀；声明行区分同文件内的同名方法。正文提及、代码围栏中的示例、其他文件的同名函数均不算覆盖。不存在的文件、未纳入清单的新函数、过期清单均失败。零函数文件必须真实存在，并在正文标题中写完整路径。

清单记录有函数体的命名函数；`extern` 外部声明在所在文件的 ABI/依赖段解释，不冒充本仓库实现。现有清单保留测试辅助函数以便对账，但测试代码不属于本轮讲解验收范围。构建入口包含在清单中。

**覆盖检查只证明结构对应，不能证明正文准确。** 每条正文仍须对照函数体及调用契约审核；不得以标题数或脚本成功代替语义核查。
